## 任务理解

golden 公式不是简单地对 `GK` 和 `GR` 都套 `SUMIFS(...,GO,"yes")`。它在 `GK` 部分使用 `">0"` 与 `GO="yes"` 条件，在 `GR` 部分使用 `_xlfn.AGGREGATE(9,6,GR3:GR21)` 汇总并忽略错误。

## agent 解题过程

agent 加载 skill 后先检查 workbook。由于实际 sheet 名是带尾随空格的 `HR `，它多次用 `HR` 或错误引用形式检查范围，日志出现 `Sheet not found: HR`、`Sheet not found: 'HR '`。之后通过 workbook 信息确认 sheet 名，写 `/task/work/inspect_gk29.js`、`set_gk29_formula.js`，用 `getCellDatas()` 验证公式并导出。

这题存在明显操作卡点：sheet 名尾随空格导致多次 inspect 失败，且 agent 对原公式上下文的定位耗时较多。

## 输出差异

output.xlsx 无法被 openpyxl 读取，异常为 `ValueError: Unable to read workbook ... invalid XML`，具体触发点是导出的 worksheet 中存在 openpyxl 不接受的 conditional formatting `operator="notContainsText"`。golden 可被 openpyxl 读取，`HR !GK29` 为：

`=SUMIFS(GK3:GK21,GK3:GK21,">0",$GO$3:$GO$21,"yes")+_xlfn.AGGREGATE(9,6,GR3:GR21)`

直接查看 output 的 `xl/worksheets/sheet1.xml` 可见 `GK29` 被写成：

`SUMIFS(GK3:GK21,GK3:GK21,"<>#N/A",$GO$3:$GO$21,"yes")+SUMIFS(GR3:GR21,GR3:GR21,"<>#N/A",$GO$3:$GO$21,"yes")`

因此即使忽略 openpyxl 读取失败，公式逻辑也与 golden 不一致。golden data_only `GK29=692.71486185`，output 因 openpyxl 读取失败无法直接比较缓存值。

## 卡点分析

- 命令误用: 多次错误引用 sheet 名 `HR`，未保留尾随空格。
- 失败重试: 有多次 `Sheet not found` 后重试。
- API 探测: 查看 `inspect range`、`run`、`run core/ranges`。
- 硬编码范围: 写入 `GK29` 正确；公式硬编码 `GK3:GK21`、`GR3:GR21`、`GO3:GO21`，但条件逻辑错误。
- 排序/截断风险: 无排序风险。
- 验证不足: 只验证写入的公式等于自身预期，没有对比原始相邻公式或 golden 语义中的 `AGGREGATE`。
- 耗时异常: 102s，正常但有 sheet 名重试成本。
- 文件约束: 未见读取 forbidden xlsx。

## 归因分析

主因是 agent 自身公式推理错误：把题目中的第二个 SUMIFS 改造成对 `GR` 同样套 `GO=yes`，而 golden 要用 `AGGREGATE` 忽略错误汇总 `GR`。另有一个非主因工具链/导出兼容问题：output 包含 openpyxl 无法解析的条件格式 XML，使评测读取也可能失败；但公式本身已与 golden 不一致。

## 改进建议

- 处理带尾随空格 sheet 名时，应从 `inspect workbook` 复制精确 sheet 名。
- 对修公式任务，应先读取原公式和相邻同类公式，识别已有 `AGGREGATE`/错误处理模式。
- `univer export` 后如 openpyxl 无法读取，应记录为工具链兼容风险并用 zip/XML 定位，同时不要忽略公式差异。
