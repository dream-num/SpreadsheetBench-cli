## 任务理解

题目要求把其他 sheets 当前为 `Jack`、`Henry`、`Richard` 的数据合并到 `Consolidate_ALL` 的 `A:L` 第一个可用空行，并在 `L` 列标注来源 sheet；只使用其他 sheets 中黄色高亮的列，保留目标表已有数据并匹配格式，不包含列头和填充色。

## agent 解题过程

agent 多次用 `univer run` 探测 sheet 行数、方法和现有计数。核心脚本 `consolidate_missing.js` 计算每个 source sheet 已经在目标表出现的数量，只追加缺失行；它先尝试写到第 4000 行以后，遇到多次 `Range is out of bounds` 后扩展行数。随后又执行 `cleanup_blank_append.js`，清空 `3999:4998` 并把表行数设回 4000。

## 输出差异

openpyxl 可读取最终 output。`A2:L8000` 内值差异 47,975 个，格式差异 23,988 个：

- `A2:A3999` 的日期值与 golden 相同，但 number format 为 `YYYY-M-D`，golden 为 `mm-dd-yy`。
- `A4000:L4999` output 为空，而 golden 有 1000 行来自合并结果，例如 `A4000` golden 为 `2023-05-01`、`B4000` 为 `CEXTCE`、`L4000` 为 `Jack`。
- `A5000:L8000` output 为空，而 golden 还有 2998 行非空。
- 非空统计：output 在 `2:3999` 有 3998 行，`4000:8000` 为 0 行；golden 在 `4000:4999` 有 1000 行，`5000:8000` 有 2998 行。

## 卡点分析

- 多次范围越界：目标表最大 4000 行时尝试检查或写入 `3999:4998` 等范围。
- agent 先实现追加缺失数据，又执行清理脚本把刚追加的 1000 行清空并把 row count 还原到 4000，直接破坏最终结果。
- 由于只按现有 `L` 列来源计数判断缺失量，逻辑本身也有重复运行风险；如果目标已有部分来源数据，可能误判 source 行数与已合并行数。
- 格式保留不足：目标已有日期格式与 golden 不一致，追加时使用模板 style 也未最终保留下来。

## 归因分析

归因分类: agent 自身题意理解/验证问题，伴随 `univer-cli` API 使用卡点。

最终失败不是导出 bug，而是 agent 在越界后执行了错误的 cleanup，把应追加的数据清掉。`Range is out of bounds` 是过程卡点，说明 agent 对 `getRange` 当前行数校验和扩容时机掌握不足。

## 改进建议

- 对追加任务，扩容后不要用 cleanup 脚本清理目标追加区；任何清理都必须在最终验证前后重新核对非空行数。
- 验证应统计 `A:L` 非空行数和 `L` 列来源分布，确认 `Jack/Henry/Richard` 的预期数量。
- 写入前应明确“已有数据区”和“追加区”边界，避免把第一个空行误判成清理起点。
- 对格式要求，应从目标表已有数据行复制完整 cell model 或至少验证日期 number format。
