## 卡点分析

- 公式形态卡点：agent 使用 `COUNTIFS` 作为 tie-breaker；golden 使用 `SUMPRODUCT((Irow=$I$6:$Irow)*(Brow=$B$6:$Brow))`。二者在普通 Excel 语义上接近，但评测比较公式/缓存时不等价。
- 范围边界风险：agent 主排名范围写到 `$1500`，超过实际 workbook 607 行；golden 也保留 `$1500` 主范围，但 tie-breaker 只到当前行，agent 的 COUNTIFS 语义由 Excel 处理，非数组公式形态。
- 验证偏差：agent 以“无重复 rank”为主要验证目标，没有比对公式文本和缓存与 expected shape。
- 潜在 `univer-cli`/导出影响：openpyxl 看到范围外 array formula 表示变化，说明导出对数组公式形态可能会普通化；但本题 answer_position 内公式本身也与 golden 不同，不能只归因给导出。

## 归因分析

- agent 自身题意理解/推理/验证问题：主要归因。虽然业务目标接近，但没有生成 golden 期望的公式形态，也没有验证公式文本。
- skill 指引/API 文档不清：次要。公式任务应强调保留/匹配现有公式族风格，尤其是 workbook 原本使用数组/SUMPRODUCT 模式时不要随意改成 COUNTIFS。
- `univer-cli` 命令或 API 问题：可能有次要影响。证据是 output 相对 init 在范围外大量 array formula 表示从 `ArrayFormula(...)` 变为普通公式字符串；但最终失败的直接证据是 `K6:K607` 公式与 golden 不同。

## 改进建议

- 修改公式时优先沿用原公式族：既然原列是 `SUMPRODUCT` 排名公式，tie-breaker 也应使用 `SUMPRODUCT((Irow=$I$6:$Irow)*(Brow=$B$6:$Brow))`，而不是换成 `COUNTIFS`。
- 验证公式题时必须抽查首行、中间行、尾行的公式文本和缓存值，而不只验证业务性质“无重复”。
- 对大型公式范围，使用实际数据末行和 answer_position 边界做核对，避免隐含 `$1500` 范围造成不可解释差异。
- 需要进一步单独验证 `univer export` 是否会改变 xlsx 中 array formula 表示；若会，应作为 `univer-cli` 导出兼容问题记录，但不能掩盖本题公式设计差异。
