## 卡点分析

- 有命令边界问题：初始读取 `A1:D2000` 超过部分 sheet 实际行数，触发 `Range is out of bounds` 后才缩小范围。
- 有环境工具假设问题：agent 尝试使用 `jq`，但容器中不可用。
- 有 API 探测问题：第一次 `univer run` 因读取 cell value 形态判断错误，清空了目标区但没有写入 bucket，需要 debug 和重跑。
- 最终验证不足：只验证 bucket 数和公式文本，没有用导出的 `.xlsx` 或 `openpyxl` 检查 answer_position 内的静态值、`TOTAL` 标签和样式。
- 公式输出有风险：golden 是静态数值，output 是公式；导出后若公式没有缓存值，评测按 cell value/公式模型比较会失败。

## 归因分析

- agent 自身题意理解/推理/验证问题：主要原因。agent 没有按 golden 风格写 `TOTAL` 标签和静态汇总值，并把总计作为公式处理，验证也未覆盖这一点。
- univer-cli 命令或 API 问题：有具体证据但不是最终唯一根因。日志中第一次 run 脚本因 `getRawValues`/cell model 形态理解不符而未收集源行，说明 run API 取值语义对 agent 不够直观。
- skill 指引/API 文档不清：有一定证据。agent 需要额外 debug 才发现 run-layer value shape 与 pipe display output 不一致。
- 环境/模型/超时问题：无超时，但 `jq` 缺失造成一次改道。

## 改进建议

- 对汇总题，禁止仅验证公式存在；必须检查导出 xlsx 中汇总行的实际 cell value、公式字段和 `TOTAL` 标签。
- 在 prompt/skill 中加强：若 golden/题面未明确要求公式，汇总结果优先写最终值；如写公式，必须确认导出 xlsx 有可评测的 cached value。
- 对 `univer run` 读取源数据的脚本，优先用同一 API 进行最小样本校验，再执行清空目标区域。
- 对多段 answer_position，验证每段末尾 3 行，专门覆盖 total/boundary rows。
