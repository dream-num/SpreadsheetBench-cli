## 卡点分析

- agent 的业务逻辑基本正确，且借助 `Expected` sheet 验证了 append 行。
- 失败卡点在格式/空白模型保真：目标 blank 单元格应保留为 inline string 空白模型，output 变成普通 numeric blank。
- 因为 answer_position 包含大量既有行和新行，样式比较也出现 120 个差异；这可能足以触发严格评测失败。
- 范围外 `cdnr`/`Expected` 空白 cell type 也发生变化，说明问题不完全是 agent 写目标区造成，`univer-cli` 导入/导出或 workbook 保存过程也可能归一化了 blank inlineStr。

## 归因分析

- univer-cli 命令或 API 问题：有具体证据。output 相对 input 在非目标 sheet 的空白 inlineStr 单元格发生 `inlineStr -> n` 的模型变化，agent 没有写这些 sheet，指向导出/保存链路对空白 cell model 的保真问题。
- agent 自身题意理解/验证问题：次要。agent 验证了可见值和 L/M 数字格式，但没有验证 blank cell type 和全区样式。
- prompt/runner/评测流程问题：可能存在。若评测把视觉等价空白的 `inlineStr` 与普通 blank 视为不等，会导致业务正确但评测失败；但 golden 确实保留了这些模型。

## 改进建议

- 对空白敏感任务，验证 answer_position 时不要只看 display/raw value，应检查 `data_type`、样式和空白单元格模型。
- 若需要保留空白 inlineStr，可在写入时深拷贝目标行/Expected 行 cell model，再只覆盖非空字段，避免用普通 `null`/空对象替代。
- 需要为 `univer-cli` 导出链路增加最小复现：不修改 `cdnr`/`Expected`，只导出后检查空白 inlineStr 是否被归一化。
- 对评测流程，可考虑区分“可见值完全一致但 blank model 不同”的失败类型。
